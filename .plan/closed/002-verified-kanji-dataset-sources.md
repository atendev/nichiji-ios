## Question

Which verified, redistributable datasets and licenses will supply JLPT levels, Joyo grades, readings, meanings, example words, frequency order, and stroke SVG paths, and how should they be packaged in the app bundle?

## Notes

Skills: `research`, `unslop`.
Reference files: `docs/DESIGN.md`, `docs/workflow.md`.

## Resolution

This research is complete and feeds the Phase 2 service and bundle contracts.

### Decision

Use a small, generated, version-pinned dataset assembled from two upstream
sources:

1. **EDRDG KANJIDIC2** for the per-character record: literal, Unicode
   identity, readings, English meanings, stroke count, Jōyō/education grade,
   legacy JLPT field, and character frequency rank.
2. **EDRDG JMdict (English edition)** for example words, their kana readings,
   English glosses, and priority hints. Select a bounded, reviewed subset per
   kanji rather than shipping the whole dictionary.
3. **KanjiVG** for stroke-order SVG paths. Its per-character SVG files include
   stroke shape/direction/order and component metadata.

The app must not present KANJIDIC2's `jlpt` value as a current official JLPT
N-level classification. KANJIDIC2 explicitly documents that it is the
pre-2010 1–4 test and that no official post-2010 kanji lists exist. Preserve
the field as `legacyJLPTLevel` (or leave it nil) and label any derived N-level
mapping as an app heuristic. Jōyō grade and frequency are usable, but should
retain their source caveats.

### Field coverage and limitations

| `KanjiEntry` field | Source and handling |
|---|---|
| `id`, readings, meanings, `strokeCount` | KANJIDIC2 XML literal, `reading_meaning`, and `misc` entities. Keep reading type/priority metadata so on/kun/nanori are not conflated. |
| `joyoGrade` | KANJIDIC2 `misc/grade`: G1–G6 education kanji and G8 remaining Jōyō kanji. Do not treat G9/G10 jinmeiyō as Jōyō. |
| `legacyJLPTLevel` | KANJIDIC2 `misc/jlpt`; pre-2010 only. No verified current N1–N5 per-kanji list is available from the JLPT. |
| `frequencyRank` | KANJIDIC2 `misc/freq`, only for the 2,501 ranked characters. It is a Mainichi Shimbun four-year newspaper analysis and is not a general modern-frequency guarantee. Nil means unranked, not “rare.” |
| `exampleWords` | JMdict entries whose kanji form contains the character. Prefer normal visible forms; exclude `sK`, `iK`, `oK`, `rK`, and other search-only/irregular forms unless explicitly reviewed. Preserve word, reading, selected English gloss, part of speech, and JMdict sequence number. |
| `strokePaths` | KanjiVG SVG for the exact Unicode character. Keep the SVG path data and stroke order; do not convert to a font or raster image. Missing/variant glyphs must be nil and surfaced as unavailable, never silently substituted. |
| `listIndex` | App-owned deterministic order after filtering and review; it is not an upstream fact. Record the generation rule and source versions. |

JMdict does not provide a canonical “example word for each kanji” field;
the relationship is generated by matching a character against JMdict kanji
headwords. JMdict priority codes are only a rough commonness signal, not a
character frequency ranking. The Tanaka sentence corpus is not recommended
for this first bundle: its upstream documentation warns that it contains
errors and non-representative examples, although the edited subset is
available under CC-BY. Use JMdict example words now; sentence examples remain
unsupported unless separately reviewed.

### Bundle format and generation

Create a build-time importer (outside the runtime app target) that records
the exact upstream release/date, download URL, SHA-256, parser version, and
license in generated metadata. The importer should:

1. parse KANJIDIC2 XML and JMdict XML;
2. join by Unicode scalar and select the reviewed example-word subset;
3. copy the matching KanjiVG SVGs and validate that each requested character
   has the expected literal and at least one stroke path;
4. emit UTF-8 `kanji-index.json` (metadata plus ordered IDs) and
   `kanji/<hex-codepoint>.json` records, with SVG files in
   `stroke-order/<hex-codepoint>.svg`;
5. emit a bundled `DATA-SOURCES.md`/license resource for the in-app Sources
   screen (the resource is generated as part of the existing data bundle, not
   a new research note).

At runtime, decode the small index and individual records with `Bundle`
resource URLs and `JSONDecoder`; load stroke SVG text lazily. This preserves
the existing immutable `Codable` `KanjiEntry` model, avoids SwiftData for
static content, permits deterministic checksums, and prevents loading all
SVG strings at launch. Apple documents `Bundle` as the representation of
code and resources stored together, and `Codable` as conversion to/from an
external representation ([Bundle](https://developer.apple.com/documentation/foundation/bundle),
[Codable](https://developer.apple.com/documentation/swift/codable)).

### License and attribution obligations

- **KANJIDIC2 and JMdict:** EDRDG's current licence statement applies CC
  BY-SA 4.0 to these files and derived data. Include attribution, a copy of
  the licence/documentation or links, and a Sources/About screen reachable
  from the app. The licence expressly allows commercial smartphone apps and
  does not require the app's code to be open source, but data adaptations
  remain subject to the share-alike condition. EDRDG also requires a process
  for regular updates; pin and document a release and schedule a data refresh
  before shipping a stale bundle.
- **KanjiVG:** the upstream site and repository release the SVGs under CC
  BY-SA 3.0. Preserve attribution and licence text/link, and treat any
  transformed SVG/path data as a share-alike adaptation. Keep the source
  release date and repository URL in the generated metadata.
- Do not claim copyright over upstream data. Do not copy upstream licence
  text into Swift source; ship it as a bundled legal/source resource and
  link it from the in-app Sources screen. The app's own selection, ordering,
  schema, and code remain separately identified.
